# Разбор документов в JSON (Задание А — LLM Engineer)

CLI, который принимает текст счёта / КП / акта и возвращает JSON по фиксированной схеме. Главный принцип: **модели не верим**.
Ответ проходит схему (pydantic), а каждое значение — проверку «это есть в тексте документа». Что не подтвердилось — `null` + предупреждение.

## Запуск с нуля

Нужен Python 3.11+ (проверено на 3.11.9, Windows 11). Больше ничего: ключей и сети не требуется.

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

(Linux/macOS: `source .venv/bin/activate`.)

| Что | Команда |
|---|---|
| Разобрать один документ | `python -m docparse data/docs/01.txt` (или `-` для stdin) |
| **Eval на всём наборе** (вместо `make eval`) | `python eval.py` |
| Eval + список всех расхождений | `python eval.py -v` |
| Тесты | `python -m pytest -q` |

Переменных окружения для запуска по умолчанию нет. Для Ollama (по желанию): `OLLAMA_HOST` (по умолчанию `http://localhost:11434`), `OLLAMA_MODEL` (по умолчанию `qwen2.5:7b`).

Коды выхода CLI: `0` — ответ валиден; `3` — валидный ответ получить не удалось (в stdout всё равно лежит корректный пустой JSON с предупреждением `validation_failed`, причины — в stderr); `4` — модель недоступна.

## Как решён вопрос «API нет» (требование 4)

Платного ключа нет, поэтому есть три бэкенда (`--backend`):

* `ollama` — настоящая локальная модель через HTTP API Ollama, в запрос передаётся JSON-схема (structured outputs).
  **Не проверял на живой модели**: Ollama на моей машине не стоит. Проверено только: форма запроса и разбор ответа (тест с подменённым `urlopen`), и что при недоступном сервере CLI честно выходит с кодом 4. Первый же шаг, если будет Ollama: `ollama pull qwen2.5:7b && python eval.py --backend ollama -v`.
* `heuristic` — **не LLM**, а набор regex-правил (`docparse/mock_llm.py`), по умолчанию. Вызов «модели» замокан, всё остальное настоящее: промпт, парсинг, валидация, ретраи, grounding, eval.
* `naive` — тоже не LLM: нарочно «плохая модель», которая выдумывает НДС по ставке, сегодняшнюю дату, БИН «из головы», номер документа, а в трети случаев отдаёт сломанный JSON. Нужна, чтобы доказать, что защита работает.

## Как это работает

```
текст → промпт → LLM → разбор JSON → схема (pydantic) ─┬─ невалидно → ретрай с текстом ошибки (до 3 попыток)
                                                        │                └─ не вышло → пустой результат + warning, код выхода 3
                                                        └─ валидно → grounding → reconcile → ответ
```

* `schema.py` — схема. `extra=forbid`, все ключи обязательны (забытый ключ — ошибка, надо писать `null`), числа строго числа (`"186 180 тенге"` — ошибка), БИН ровно 12 цифр, дата — реальная дата в ISO.
* `pipeline.py` — цикл ретраев. Модели показывают её же ответ и список ошибок валидации. **Если и после 3 попыток невалидно — система возвращает пустой валидный результат (`doc_type=unknown`, всё `null`) с предупреждением, а не падает и не отдаёт мусор.**
* `grounding.py` — код может только **удалять** значения, которых нет в тексте (никогда не добавляет): БИН — 12 цифр отдельным токеном; дата — должна быть распознана в тексте; суммы/qty/price — должны встречаться как числа (или прописью); валюта — нужен маркер (тг/₸/$/€…); номер — только после маркера «№/No/#»; названия — подстрока текста. Поэтому НДС «по ставке» отбрасывается.
* `reconcile` — противоречия (см. правила ниже) и предупреждения о несостыковках (`line_items_sum_mismatch`, `vat_exceeds_total`, `multiple_currencies`).
* `textscan.py` — сканеры: даты (в т.ч. «09 қазан 2026»), числа, суммы прописью (рус. и каз.), OCR-нормализация.

## Правила, которые я выбрал (неоднозначные места ТЗ)

1. **Две разные даты выдачи** → `doc_date` = первая по тексту, предупреждение `doc_date_conflict`. Дата после «действительно до/срок» — не дата документа и конфликтом не считается (Документ 2: `doc_date` = 05.11, а 30.11 — срок действия).
2. **Два разных «итого к оплате»** → `total_amount` = первое по тексту, предупреждение `total_conflict`. Правило применяет код, а не модель (в `test_conflicting_dates_and_totals…` модель «выбирает» второе — код возвращает первое).
3. **`total_amount` — сумма к оплате с НДС** («Всего к оплате»), а не «Итого» без НДС. В Документе 1 это 186 180, не 160 500; противоречием это не считается, потому что у метки «к оплате» приоритет.
4. **НДС**: только если сумма написана. «НДС не облагается», «Без НДС», «not applicable» → `null` (не `0`: ноль — тоже утверждение, которого в документе нет).
5. **Поставщик** — «Исполнитель/Поставщик/Продавец/Seller», а не заказчик. БИН заказчика (Документ 5) в `supplier_bin` не попадает. Двуязычное «ЖШС … / ТОО …» → беру русскую форму.
6. **Документ 3, номер и дата.** В строке `№ AKT-09 / 09 қазан 2026 ж.` читаю номер = `AKT-09`, дата = `2026-10-09` (после «/» стоит дата словами). Другая трактовка — номер `AKT-09/09` — возможна; я не стал угадывать молча и фиксирую выбор здесь. Тип — `invoice` («Шот-фактура» = счёт-фактура).
7. **OCR.** Буквы-двойники в числовых токенах (`O/О→0`, `l/I→1`, `З→3`) исправляются, но с предупреждением `ocr_repaired` и пониженной уверенностью 0.6 (вместо 0.95). Это не «выведение БИН», а чтение того же числа. Названия и номера документов не «лечатся».
8. **`field_confidence`** считает код по тому, как значение найдено в тексте (как есть 0.95 / прописью 0.85 / после OCR-исправления 0.6), и берёт минимум с самооценкой модели. Для `null`-полей ключа нет.
9. Если нет ни одной метки валюты — `currency: null`, даже для документа на русском. Валюту «по умолчанию KZT» не подставляю.

## Тестовый набор и eval

`data/docs/` — 10 документов, `data/gold/` — эталоны (писал вручную, независимо от экстрактора; проверяются схемой в тестах).
01–03 — ваши. Мои 04–10: счёт на английском в USD (04); акт, где у исполнителя нет БИН, а у заказчика есть (05); КП без даты, итога и НДС (06); два разных дня и две разные суммы «к оплате» (07); сильные OCR-ошибки (08); письмо, не являющееся документом — всё `null` (09); сумма с копейками и пробелами «1 234 567,89» (10). Сложные: 03, 05, 06, 07, 08, 09.

`python eval.py` печатает по каждому полю: верно / галлюцинации (в эталоне `null`, поле заполнено) / пропуски (в эталоне есть, дали `null`) / неверно (значение есть, но другое), плюс число позиций line_items, найденность ожидаемых предупреждений и сколько раз сработал ретрай.

Результаты (90 ячеек = 10 документов × 9 полей):

| бэкенд | guard | точность | галлюцинации | пропуски | неверно | ретраев |
|---|---|---|---|---|---|---|
| `heuristic` | on | 100% | 0 | 0 | 0 | 0 |
| `naive` | **off** | 86% (77/90) | **13** | 0 | 0 | 3 |
| `naive` | on | 100% | 0 | 0 | 0 | 3 |

**Как читать эти цифры честно.** 100% у `heuristic` ничего не говорит о качестве настоящей LLM: правила писались, глядя на эти же 10 документов (это «обучение на тесте»). Ценность таблицы — в строках `naive`: без защиты «модель» выдумывает 13 значений (БИН, НДС, даты, номера), с защитой — ноль, а сломанный JSON исправляется ретраем (3 из 10). Реальную точность покажет только `python eval.py --backend ollama` — это не запускал.

Один баг, который eval поймал на мне: сначала проверка номера была «значение есть где-то в тексте», и выдуманный номер `1` проходил (цифра 1 есть в любом документе) — 2 галлюцинации у `naive` даже с guard. Теперь номер должен стоять после «№/No/#», есть тест `test_generic_doc_number_is_not_accepted_without_marker`.

* Ставка НДС 16% нигде не зашита; ничего не считаем и не «догадываемся».
