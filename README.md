# Разбор документов в JSON (Задание А — LLM Engineer)

CLI: принимает текст счёта / КП / акта, возвращает JSON по фиксированной схеме через Gemini. Принцип: **модели не верим** —
ответ проходит схему (pydantic), а каждое значение проверяется на «это есть в тексте документа». Не подтвердилось → `null` + предупреждение.

## Запуск с нуля

Нужен Python 3.11+ и **ключ Google AI (Gemini API)**. Модель по умолчанию — `gemini-3.8-flash` (`--model` или `GEMINI_MODEL` меняют её).

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
$env:GOOGLE_API_KEY="ваш_ключ"
```

(Linux/macOS: `source .venv/bin/activate`, `export GOOGLE_API_KEY=...`.)

| Что | Команда |
|---|---|
| Разобрать документ | `python -m docparse data/docs/01.txt` (или `-` для stdin) |
| **Eval на всём наборе** | `python eval.py` (`-v` — все расхождения, `--no-guard` — без защиты, для сравнения) |
| Тесты (ключ и сеть **не нужны**) | `python -m pytest -q` |

Коды выхода CLI: `0` — ответ валиден; `3` — валидного ответа получить не удалось (в stdout всё равно корректный пустой JSON с `validation_failed`, причины в stderr); `4` — модель недоступна (нет ключа, сеть, лимиты).

Без ключа работают только тесты: они гоняют пайплайн на скриптованной «модели» и проверяют поведение системы (ретраи, fallback, отбрасывание выдумок, правила противоречий). Eval без ключа не запустится — он по определению гоняет настоящую модель.

## Как это работает

```
текст → промпт → Gemini → разбор JSON → схема (pydantic) ─┬─ невалидно → ретрай с текстом ошибки (до 3 попыток)
                                                           │               └─ не вышло → пустой результат + warning, код выхода 3
                                                           └─ валидно → grounding → reconcile → ответ
```

* `schema.py` — схема: `extra=forbid`, все ключи обязательны (надо писать `null`, а не пропускать), числа строго числа, БИН ровно 12 цифр, дата — реальная дата ISO.
* `pipeline.py` — цикл ретраев: модели показывают её ответ и список ошибок. Если после 3 попыток невалидно — **пустой валидный результат** (`doc_type=unknown`, всё `null`) с предупреждением, а не исключение и не мусор.
* `grounding.py` — код может только **удалять** то, чего нет в тексте: БИН — 12 цифр отдельным токеном; дата — распознана в тексте; суммы/qty/price — есть как числа или прописью; валюта — есть маркер; номер — стоит после «№/No/#»; названия — подстрока. НДС «по ставке» отбрасывается. Затем `reconcile` применяет правила противоречий и добавляет предупреждения (`line_items_sum_mismatch`, `vat_exceeds_total`, `multiple_currencies`).
* `textscan.py` — сканеры для проверок: даты (в т.ч. «09 қазан 2026»), числа, суммы прописью (рус./каз.), OCR-нормализация. LLM тут нет.
* `llm.py` — вызов Gemini по REST (ключ только из окружения, в заголовке), `prompts.py` — промпт.

## Правила, которые я выбрал (неоднозначные места ТЗ)

1. **Две разные даты выдачи** → `doc_date` = первая по тексту, предупреждение `doc_date_conflict`. Дата после «действительно до/срок» — не дата документа (Документ 2: 05.11, а 30.11 — срок).
2. **Два разных «итого к оплате»** → `total_amount` = первое по тексту, `total_conflict`. Правило применяет код, а не модель.
3. **`total_amount` — сумма к оплате с НДС**. Документ 1: 186 180, не 160 500.
4. **НДС** — только если сумма написана. «Не облагается», «Без НДС» → `null`, не `0`: ноль — утверждение, которого в документе нет (код не подтверждает 0 никогда).
5. **Поставщик** — исполнитель/поставщик/продавец, не заказчик; БИН заказчика (Документ 5) в `supplier_bin` не попадает. Двуязычное название → русская форма.
6. **Документ 3:** в `№ AKT-09 / 09 қазан 2026 ж.` номер = `AKT-09`, дата = `2026-10-09`. Возможна трактовка «номер `AKT-09/09`» — выбор зафиксирован здесь. «Шот-фактура» = `invoice`.
7. **OCR:** `O/О→0`, `l/I→1`, `З→3` в числовых токенах исправляются, но с предупреждением `ocr_repaired` и уверенностью 0.6. Названия не «лечатся» (поэтому см. ниже Документ 8).
8. **`field_confidence`** считает код по способу нахождения (как есть 0.95 / прописью 0.85 / после OCR 0.6), берёт минимум с самооценкой модели. Для `null` ключа нет.
9. Нет маркера валюты → `currency: null` (не «по умолчанию KZT»).

## Тестовый набор и eval

`data/docs/` — 10 документов, `data/gold/` — эталоны (вручную; схемой проверяются в тестах). 01–03 — ваши. Мои 04–10: счёт на английском в USD (04); акт, где у исполнителя нет БИН, а у заказчика есть (05); КП без даты, итога и НДС (06); две даты и два «итого» (07); сильные OCR-ошибки (08); письмо, не документ — всё `null` (09); сумма с копейками «1 234 567,89» (10). Сложные: 03, 05, 06, 07, 08, 09.

`python eval.py` печатает по каждому полю: верно / **галлюцинации** (в эталоне `null`, заполнено) / **пропуски** (в эталоне есть, дали `null`) / неверно (другое значение), число позиций, найденность ожидаемых предупреждений и число ретраев.

Результат на `gemini-3.8-flash` (90 ячеек = 10 документов × 9 полей): **99% (89/90), 0 галлюцинаций, 0 ретраев**. Единственная ошибка не постоянная: в одном прогоне Документ 8 дал пропуск, в другом Документ 3 — позиция названа только по-русски (`Оказание услуг` вместо двуязычной строки). LLM недетерминирована, цифры слегка плавают от запуска к запуску.

Что показал первый прогон и что я исправил: (а) модель клала в `field_confidence` ключ `line_items`, мой валидатор его отвергал → 9 ретраев из 10; (б) «НДС не облагается» модель превращала в `vat_amount=0`, а проверка «число есть в тексте» принимала ноль из «00 тиын»; (в) двуязычное имя поставщика возвращалось целиком — добавлено правило в промпт. Раньше ещё ловил: выдуманный номер `1` проходил проверку, потому что цифра 1 есть в любом тексте — теперь номер обязан стоять после «№/No/#».

Документ 8: когда модель «исправляет» OCR прямо в названии (`Цемент М4ОО` → `М400`), строки `М400` в тексте нет, и защита отбрасывает позицию. Это сознательно консервативно.

**Честно о цифрах:** промпт и правила я подгонял под эти же 10 документов, поэтому 99% — оптимистичная оценка для реальных документов клиента.
